## 前言

毕设是做图像的深度学习压缩，9 月中左右基本结束了第一阶段的训练，按计划准备做部署。结果做量化的时候越做越不对劲，问题就像滚雪球一样越滚越大，给自己吓得够呛...

## 背景

9 月这段时间好的大模型发了很多，就包括了有视觉能力的 [GLM-5.3-Flash](https://z.ai/blog/glm-5.3-flash) 和 [Deepseek-V4.1-Flash](https://www.deepseek.com/en/news/deepseek-v4-1-flash/)，感觉比较好用就买了 GLM 的 Coding Plan，到 20 号为止一直有夜间畅用活动，13 号这晚是打算用这次常用看能不能把量化的过程搞通。

## 问题的调查

### 发现问题

让 ZCode 搞了一下量化的流水线，一共有这么 5 步：

1. LoRA 折叠（merge）
2. ONNX 导出（export）
3. 校准数据（calib）
4. 对拍验收（parity）
5. INT8 转换收尾（convert）

[pixi 工具本身能折腾多环境]({% post_url 2026-02-08-Pixi：现代化的跨平台环境管理 %})，在 14 号凌晨按流程*正常*配完环境，就开始跑工作流。跑到第 5 步 GLM 估计是要俩小时左右，毕竟作为自己做的东西还是要解释的，就问了 GLM 这些脚本的工作流，一边就在看交付物。

差不多是凌晨 4 点，看到 parity 的交付物，它验收的是量化（INT8）之前三条 fp32 路径的一致性，数据比较好看：

| 对比          | x0 max\|Δ\| | 图像 PSNR | 阈值         |
| ------------- | ----------- | --------- | ------------ |
| merge vs 原版 | 1.0e-3      | 76–81 dB  | 1e-3 / 50 dB |
| ONNX vs 原版  | 6.7e-4      | 78–82 dB  | 1e-2 / 40 dB |

但是交付的文件却是糊的，而且文件名是 validation 的文件带上后缀，感觉是由其产生的，成对的文件倒是蛮像。按照 GLM 的口吻，这其中有原始模型重建出来的。

这就说不过去了！

同一批图，同模型同码率在评测管线里的重建是 27.8dB 的正常照片，立马开了个 tmux 测重建，11-14dB，这个结果显然是不可接受的，量化糊掉也就算了重建居然也错了；我寻思可能也就 GLM 新写的 pipeline 就错了重写就是了，但是 GLM 宣称 pipeline 是完全按照旧的 Encode-Decode 结构去写的，这就很匪夷所思了。

继续查 diff 也没有任何发现。我库里还留着一些旧版本模型的 inference 管线，顺便跑了跑，一跑给自己吓个半死：怎么这些都跑不通了，全糊成这样？如果这个问题不能解决的话，意味着我前面一年半所做出来的 checkpoint 将全部废掉，只有留作 ablation 的样张和单数据集上的结果。

### 定位问题

还算是这个模型比较友好。对于一张图片的压缩和解码，通常是 `image -> bitstream -> image` 的路线，会留一个中间文件也就是流文件。用流文件直接走 Decoding 发现还是重建不出来，加上其他旧模型的代码零改动却也一起糊了（zero diff），基本可以确定是环境坏了，而且至少是 Decoding 这步坏了，而 Encoding 路径因为新的 Decoding 路径已经覆盖无法确认其好坏。

重配了几遍的环境 Python 部分，用的包管理器 pixi，除了量化部分的环境有变化以外基本还是无 diff，目光就聚焦到了 cpp 的代码上，这部分是用于处理熵编解码器的。

### （暂时）解决问题

在 tmux 日志里翻了很久，算是在 2000 行的窗口里面找到下面两句：

```
09-14 01:48  src/modules/entropy/MLCodec_CXX.cpython-310-x86_64-linux-gnu.so
09-14 01:48  src/modules/entropy/MLCodec_rans.cpython-310-x86_64-linux-gnu.so
```

**这说明熵编码器的编译产物被重编过。** 01:48，正是 `pixi install` 装完新环境之后，顺手跑 `build_coder` 做量化前置检查的那几分钟。rANS 这类整数位流代码对编译器优化极其敏感（进位处理、别名、溢出，全是 UB 高发区），新工具链 + LTO 一上，有损编码就这么来了，而且损失极其严重（LTO 只是头号嫌疑：后来按 OneDC 原版 readme 配方复刻的无 LTO 构建同样失败，本地重编这条路是整条堵死的）。

个人推测可能存在 build 文件版本不对的问题，很自然的想到遇事不决重装，尤其是 cpp 的部分，但依旧无济于事，可能依赖关系改了。翻出 tmux 里残存的构建日志，三行关键信息：

```
-- The CXX compiler identification is GNU 14.3.0
-- Performing Test HAS_FLTO - Success
Cloning into 'pybind11-src'... HEAD is now at 5b0a6fc
```

也就是说这次重编：conda gcc **14.3**（相当新）、**LTO 开启**、pybind11 是**构建时实时 clone 的 master**——每次重编拿到的版本都不一样。**MLCodec\_\*.so 在被新工具链（conda gcc 14.3 + LTO + 漂移的 pybind11 master）重编后，rANS encode/decode 不再自洽，产生有损码流，导致压缩管线全部输出糊图。**

而原始那个能用的 .so，是几个月前项目初始化时用 Opencode + MiniMax 构建的，conda/uv 环境配的很齐全但 cpp 部分怎么搞的无从考证，这就很头痛了。

一筹莫展之时，交给 AI grilling，没想到还真问出点东西。把本地重编的路堵死之后，修复思路反而简单了：在这套熵编码代码里面找到了文件头版权——`rans.cpp`/`ops.cpp` 第一行写着 _Copyright 2020 InterDigital Communications, Inc._（正是 [CompressAI](https://github.com/interdigitalinc/compressai) 的出品方）；外层的 pybind 包装是 _Copyright (c) Microsoft Corporation_，所谓 [MLCodec](https://github.com/microsoft/dcvc) 就是微软拿 CompressAI 的 rANS 核心包的自家接口，而 **CompressAI 在 PyPI 上有官方预编译 wheel**——它的 CI 用成熟工具链构建、被全世界用了五年。于是装上 CompressAI 的官方预编译 wheel，参照它的源码针对本任务 vibe 了一下，重写为 compressai 1.2.6 适配层，就可以继续推进任务了。

## 感想

### 别乱动 lockfile

通俗地说，就是引入新依赖 -> lockfile 重解算（而且由于新包可能不兼容，不动 lockfile 可能无解）-> 一次前置检查顺手触发的重编译 -> 唯一可用的预编译 .so 被覆盖且无备份。环环都错，但最不应该的是动 lockfile：它的本职就是钉死版本、让下次装出来的东西和这次一模一样，toml 里 `*` 这种宽约束根本撑不起可复现；一重解，编译器工具链这种环境成分就悄悄换了血，后面那记重编译只是补刀。

仔细想想的话就会发现，其实存在一种更危险的可能：如果整个模型集是在一个*有点问题*的 build 上跑出来的，那么这次更新的 build 后，由于部署需要，整个检查点谱系可能就全废了得重跑，可能还有非预期的性能下降，这就要老命了。通常来说，需要走备份流程的都是源码、权重、码流、重建图、数据集，build 一般总会被列入 `.gitignore`。没有人会想到，`src/modules/entropy/` 下两个不起眼的构建文件 `.so` 也是资产——源码在、构建方式没了，重编即坏，覆盖即失；如果是 docker/nix 大概就不会有这种问题了吧。

不过现在这个项目换了更稳定的 compressai：官方 wheel 装完即用，而且刻意留在 lockfile 外——sdist 一进 lock，每次 `pixi install` 都会现场重编 rANS，等于把事故成因固化成流程。本地 .so 路线就此退役，应该问题不大了。

### 天下没有免费的馅饼

整个事故发生在 GLM 免费蹬时期，晚间免费名义上是用量低峰，实际上应该也会有不少 token plan 的付费用户为了薅羊毛要在这段时间大幅提高用量，这段时间明显感觉免费蹬的 GLM-5.3-Flash 有智力水平下降的问题，吐字 tps 降了不说还雷霆大思考，单会话花时间不说质量也没有往常那么高，如果真恢复不了，真不知道后续该如何是好；本来就高血压，为了贪这点小便宜给自己搞病了也得不偿失，也算长个教训了。
