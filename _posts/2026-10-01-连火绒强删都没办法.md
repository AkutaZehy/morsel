> 起因是给 C 盘和 D 盘做容量盘点，撞上几个怎么删都删不掉的东西：休眠文件的"尸体"、一整套旧系统克隆、还有一个叫 NUL 的文件。右键强删、安全软件轮番上阵全部失败。写这篇把"删除失败"这件事一次讲透。

## 当你删除一个文件时，Windows 在做什么

`DeleteFile("D:\foo.txt")` 在返回"成功"之前，要连续闯三道关：

1. **路径解析关**：Win32 子系统先规范化路径——检测 DOS 保留名、检查 260 字符上限、解析相对路径与符号链接；
2. **权限关**：安全参考监视器检查调用者令牌对该文件的 DELETE 权限（或对父目录的"删除子项"权限）；
3. **占用关**：内核检查该文件已打开的句柄与共享模式——若现有句柄当初未授予 `FILE_SHARE_DELETE`，删除直接失败，错误码 32（ERROR_SHARING_VIOLATION）。

任何一关失败，你看到的就是"文件已在另一个程序中打开"或"拒绝访问"。三道关，也决定了后文的三类解法。

## Windows 的权限组运作

常见账户组从低到高：

- **Guests**（`S-1-5-32-546`）：来宾，几乎只读；
- **Users**（`S-1-5-32-545`）：标准用户，日常软件运行在这一级；
- **Administrators**（`S-1-5-32-544`）：管理员组；
- 再往上才是 **SYSTEM**（`S-1-5-18`，操作系统本体与服务的运行身份）与 **TrustedInstaller**（`NT SERVICE\TrustedInstaller`，Windows Modules Installer 服务，系统文件与 WinSxS 的默认所有者）。

**SID 的命名规则**，以 `S-1-5-32-544` 为例：

- `S`：固定前缀；`1`：修订版本号，SID 问世以来一直是 1；
- `5`：标识符颁发机构，5 = NT Authority；
- `32`：第一个子授权，决定命名空间——`21` = 由本机或域自行发放（所以每台机器唯一的 SID 都长成 `S-1-5-21-...`），`32` = 内置域（Builtin，全球 Windows 通用常量）；
- `544`：相对标识符（RID），内置域内的固定编号：544 Administrators、545 Users、546 Guests。同一思路下，`S-1-5-21` 命名空间里 RID 500 永远是内置 Administrator 账户、501 是 Guest。

一个常见误解是"管理员 = 最高权限"。管理员的"万能"来自令牌中的特权（如 `SeTakeOwnershipPrivilege`），而这副完整令牌默认是锁着的：

- **普通 cmd / 终端**：即便用管理员账户打开，进程拿到的也是 UAC 过滤令牌——管理 SID 被剥离、特权未激活，实际运作在标准用户一级，连 `takeown` 都会报"拒绝访问"；
- **管理员 cmd / 终端**："以管理员身份运行"后进程换用完整令牌，特权激活，才有资格接管所有权。

NTFS 每个文件带一个安全描述符：所有者（Owner）+ 自主访问控制列表（DACL）。删除需要 DACL 上的 DELETE 权限，或对父目录的"删除子项"权限。持完整令牌的管理员最终删得掉一切，但路径固定为三步：takeown 接管所有权 → 重写 DACL → 删除。

## 文件"占用"

占用的本质是共享冲突。进程用 `CreateFile` 打开文件时要声明共享模式（`FILE_SHARE_READ / WRITE / DELETE`）；常见的播放器、编辑器、IM 打开文件时不授予 `FILE_SHARE_DELETE`，此后任何删除请求都会撞上 ERROR_SHARING_VIOLATION——这关与权限无关，管理员身份也没用。

典型场景：被播放器锁住的视频、进程加载中的 DLL 与正在运行的 exe、被服务挂住的数据库文件。

**排查谁占用了文件**，业界是两条路线：

- **句柄枚举**：遍历系统全部打开句柄，匹配目标路径。资源监视器（`resmon` → CPU → "关联的句柄"）与 Sysinternals 的 `handle.exe -a <文件名>` 走这条路，重，但什么句柄都逃不掉；
- **Restart Manager**：Windows 为安装/更新场景设计的官方 API（`rstrtmgr.dll`），注册目标文件后由系统直接报告哪些进程阻止你操作它，语义干净、开销小。[FileUtil](https://github.com/xuanli199/FileUtil)（AI 编写的 C# 占用检测器）就是它的封装。

**解除占用**：关掉占用进程是唯一的即时手段；进程关不掉时，把删除登记为"重启后执行"（`MoveFileEx` 的 `MOVEFILE_DELAY_UNTIL_REBOOT`，落在注册表 `PendingFileRenameOperations`，开机时由 SYSTEM 身份的会话管理器代为完成）。

## 常见删除手段盘点

- **选中右键 / Del 键**：资源管理器执行的是"移入回收站"（实际是移动到卷根的 `$Recycle.Bin`），Shift+Del 才直接调删除 API。explorer 始终以过滤令牌运作，DACL 一高就报错；
- **杀软 / 清理工具的"强删""粉碎"**：三板斧——改 DACL 后删、解除占用句柄后删、登记 `PendingFileRenameOperations` 重启代删。第三招动得了 SYSTEM 文件，但路径解析发生在 API 层，对保留名与深路径照样失效；"粉碎"（覆写内容）只保证不可恢复，与权限无关；
- **cmd / bash 的 del、rm**：与资源管理器走同一批 API，普通终端的令牌级别也相同，删不动高权限文件的原因一致；Git Bash 的 rm 换汤不换药，MSYS 层不会替你突破 ACL；
- **右键转移所有权后删**：属性 → 安全 → 高级 → 更改所有者（勾选"替换子容器和对象的所有者"）→ 授予完全控制 → 删。这是 takeown /r + icacls /grant /t 的图形版，等价于三步链，同样会卡死在深路径上。

三道关里，图形手段至多通两道。全通的只剩命令行三步链（权限型）与 `\\?\` 前缀（异常型）。

## 两个实战案例

### 案例一：权限高于管理员的文件

**hiberfil.sys 尸体**：休眠文件只存在于当前系统盘，其他盘上这份是搬盘/重装的遗物。识别特征：时间戳停在过去（本例 2024-02-08 后再无写入，而系统盘的活体仍在更新）。它的 DACL 仅 SYSTEM，管理员组不在列表中，删除前连改权限的资格都没有。

**旧系统克隆树**：重装残留的整套 `Windows`、`Program Files`、`Users` 目录结构，文件属 SYSTEM/TrustedInstaller 所有，还夹杂超过 260 字符的深路径。

处理（管理员 cmd，三步链：接管所有权 → 授予权限 → 删除）：

```cmd
:: 单文件
takeown /f D:\hiberfil.sys
icacls D:\hiberfil.sys /grant *S-1-5-32-544:F
del /f /a D:\hiberfil.sys

:: 目录树
takeown /f D:\mount /r /d y
icacls D:\mount /grant *S-1-5-32-544:F /t /c /q
rd /s /q D:\mount
```

> `*S-1-5-32-544` 的星号表示按 SID 而非名字解析，不受系统语言与组重命名影响。
> {: .prompt-tip }

### 案例二：不该存在的文件

**DOS 保留名文件**（`NUL`、`CON`、`LPT1`、`AUX` 等）：Win32 子系统在路径解析层就把 `NUL` 解析为设备而非文件名，常规 API 根本创建不出来；但 AI 生成命令或脚本时，可能借 `\\?\` 前缀这类 NT 层路径绕过解析，真的写出名叫 `NUL` 的文件。此后资源管理器与常规 `del` 对它的每次尝试都被解析成设备，永远扑空。

**深路径文件**：名字合法，但完整路径超过 MAX_PATH 的 260 字符上限，资源管理器与多数程序打不开也删不动。

处理：核心是 `\\?\` 前缀——跳过 Win32 的保留名解析与 MAX_PATH 限制，直接在 NT 层按字面路径访问。

```cmd
:: DOS 保留名（NUL 等）：\\?\ 前缀后接完整绝对路径
del /f /a "\\?\D:\path\to\NUL"

:: 深路径：同前缀直接删
del /f /a "\\?\D:\very\long\path\file.ext"

:: 整棵深路径目录树：robocopy 镜像清空法兜底
mkdir D:\__empty
robocopy D:\__empty "D:\very\long\dir" /MIR
rd /s /q "\\?\D:\very\long\dir"
rd D:\__empty
```

## 顺带：海量小文件删除为什么慢

删除的代价正比于文件个数，而不是文件大小——每个文件都要走一遍独立的元数据事务：MFT 记录回收、目录索引更新、USN 日志记账。20 万个小文件的删除成本等于 20 万个大文件，几十秒到几分钟是 NTFS 的正常发挥。两个放大器：Defender 等过滤驱动在每次文件操作上插回调；PowerShell 的 `Remove-Item -Recurse` 为每个文件构造 .NET 对象，比 cmd 的 `rd /s` 慢一大截。

一个反证是快速格式化：1TB 的卷几秒钟就能完成。文件在磁盘上本来就是"数据块 + MFT 元数据记录"两样东西分开存的，文件名与路径只存在于元数据里；快速格式化不碰任何数据块，只重置 $MFT、簇位图这几个顶层账本，账本一清，所有文件同时"消失"——和逐文件删除完全不是一个量级。这也是快速格式化后数据能被恢复工具捞回来的原因：丢的只是索引，数据块原封未动。

权限型场景（案例一）没有捷径：takeown、icacls、删除各是一轮 O(n) 元数据写，加起来就是三轮，robocopy 也不携带 DELETE 权限，没有接管所有权前它照样成片失败。

而无 ACL 障碍的海量目录（`node_modules`、构建产物），有一步很值的优化——**先改名闪避，再慢慢删**：

```cmd
:: 同卷改名是 O(1) 元数据操作，瞬间完成，项目立刻解锁
ren node_modules node_modules.trash

:: 后台慢慢删，选快的实现
mkdir D:\__empty
robocopy D:\__empty "D:\project\node_modules.trash" /MIR
rd /s /q "D:\project\node_modules.trash"
rd D:\__empty
```

`robocopy` 全名 Robust File Copy，本职是复制，删除能力藏在 `/MIR`（等价于 `/E` + `/PURGE`）里：镜像模式要求目标与源严格一致——源里有的，目标必须有；源里没有的，目标不许有。源是个空目录，于是"补"为零、"删"为全部，删除成了复制的对偶面。相比三步链，它省掉了 takeown 与 icacls 两整轮权限写，内部多线程流水线加长路径形式访问，260 字符限制天然免疫。它一定比"直接删"快吗？分对手：对比 `Remove-Item -Recurse` 几乎必胜——.NET 对象开销是纯税；对比 `rd /s /q` 则看场景——rd 是单线程深度优先，每个文件的删除延迟（内核遍历、安全检查、过滤驱动回调链）串行累加，robocopy 的多线程把不同目录的删除流水线化，让这些等待互相重叠；这在 SSD 上收益明显，元数据事务没有机械寻道惩罚，并行吃得满队列深度；换到机械盘，随机小 IO 本身就是瓶颈，并行加剧寻道，两者往往打平。物理下限在那里——工具优化的只是常数系数。

## 与 Linux 的差异

- **权限挂在哪**：Linux 的 rwx 是资源的属性（owner/group/other 三组位，没有"拒绝位"）；Windows 是资源挂 ACL，每条 ACE 指向具体 SID、允许或拒绝、沿父目录继承；
- **提升语义**：Linux 的提升是"换人"——`sudo` 之后你就是 root（UID 0），内核对 UID 0 无条件放行；Windows 的提升是"换令牌"——账户没变，从过滤令牌切到完整令牌，特权才生效；
- **删最高权限文件的体验**：root 删自己的文件 `sudo rm` 一步到位；Windows 管理员面对 SYSTEM/TrustedInstaller 的文件，仍要走 takeown → icacls → del 三步；
- **占用语义**：Linux 删除看的是对父目录的写权限，文件本身开着也能删（unlink 后由句柄持有者用完即散）；Windows 把"是否允许共享打开"交给第一个打开者的自愿声明，于是有了"文件被占用"这门独有学问。
